# Experimental native RGB+IR on Surface Book 2

**Status:** Approved 2026-11-27 for planning [Stage A](#1-bound-the-first-engineering-slice) only; that approval accepts no later scope. G0 was accepted separately, in [ADR-0042](../../architecture/adr/0042-embedded-book2-rgb-ir-class.md) on 2026-11-28. The selected direction is supervised split capture first, with KDE/SDDM/KWallet as the reference desktop. This document does not amend an ADR, authorize a live test, or enable an experimental path.

**Baseline:** [Irlume `4b4f9330`](https://github.com/archledger/irlume/commit/4b4f9330d9a4cfcb7d96add64e3954d27a6ae5e3) and [issue #1379](https://github.com/archledger/irlume/issues/1379). [Proposed ADR-0041](../../architecture/adr/0041-admission-first-embedded-ir.md) defines admission boundaries but selects no approved production embedded class. [Accepted ADR-0003](../../architecture/adr/0003-fingerprint-keyring-unlock.md) is the existing wallet delivery contract, not an authorization for the new class.

## Intent and scope

Deliver one default-off experimental feature for an exact qualified 13.5-inch `Surface_Book_1832` configuration: real native RGB+IR enrollment, PAM face authentication, warm screen unlock, and cold local sign-in that opens the same existing encrypted KWallet. Diagnostics are an intermediate test stage. Catch build, lifecycle, policy, PAM and rollback failures locally before a scoped request to a Book 2 operator.

- First hardware reference: Core i5-7300U, UEFI reported as `394.779.768`, front OV5693 RGB, OV7251 IR, shared IPU3 CIO2 and separate ImgU. The [current reporter reply](https://github.com/archledger/irlume/issues/1379#issuecomment-7229600363) reports `7.3.5-arch1-1-surface`, a rebuilt OV7251 DKMS backport and a local libcamera 0.8.0 build. That identifies a lead, not an allowlist or a pinned loaded stack. The [earlier observation](https://github.com/archledger/irlume/issues/1379#issuecomment-7144057589) was one front RGB frame only.
- First desktop reference: Arch x86_64, Plasma Wayland 6.8.3, KScreenLocker 6.8.3-1, SDDM 0.21.0-7, `kwallet-pam` 6.8.3-1, KWallet 6.32.0-1, and `pambase` 20260616-1. Pin Linux-PAM, systemd, effective PAM includes, worker/session identity, greeter mode and wallet provider before testing. These are reference versions, not an assumption about the reporter's installed desktop. Recheck drift; do not ask them to downgrade.
- Non-goals: other SKUs/IPU generations, rear RGB, virtual or loopback endpoints, concurrent capture, integrated IR-only enrollment, GNOME/COSMIC, remote login, autologin, privileged elevation, app consent, generic credential APIs, arbitrary wallet kinds, and any modification to ordinary USB, fingerprint or password semantics.

## Approaches

| Approach | What we gain | Cost and limit |
| --- | --- | --- |
| **Selected: supervised sequential split** | Reuse libcamera v0.8.0 ImgU/IPA for processed RGB; use a dedicated native CIO2 multi-planar `ip3y` adapter for IR. Start testing the two lifecycles and their handover without implementing an ISP. | Two backends and two graph lifecycles. A trusted owner and trustworthy hardware-stop observations are prerequisites. Not a stock-desktop route today. |
| Coordinated upstream pipeline first | Explicit selection and one pipeline lifecycle can reduce duplicate graph transitions and place stop evidence at its source. | Requires wider downstream/upstream integration. A single pipeline still does not fence independent opens or prove optical OFF; sequential coordination alone does not solve insufficient timing. |

Use the split for the first proof build, not as a commitment to ship it. If a reviewed design cannot enforce pre-discovery ownership or observe decisive teardown states on the split, or measured timing cannot meet the approved paired-input contract, stop that route and evaluate coordinated upstream changes. If independent optical qualification or an adequate unattended OFF contract cannot be established, keep real activation disabled regardless of architecture. Do not ship around a missing proof.

## 1. Bound the first engineering slice

Design approval would allow planning **Stage A only**, a private, non-authenticating utility scope under ADR-0041's phasing. It does not accept G0 or the later scopes. Stage A is a **private, non-granting, no-device build**: declaration and link witnesses for the native API boundary, a fixture-driven supervisor lifecycle and failure verifier, and an offline `ip3y` payload check. Build or discover a private exact libcamera SDK and handler/IPA; no system-wide install. Verify real library symbol resolution and the native headers rather than inferring ABI compatibility from headers alone. The linked witness must not enumerate or start a manager. No real camera adapter bodies that open, stream, change links or control an emitter in Stage A. Run fixtures in a disposable environment with no real capture device, host seat, daemon socket, or credential store. Fixture evidence cannot cross into the production authority path. No PAM wiring, enrollment file or activation switch in this slice. Obtain an explicit G0 decision and exact-device backend design review before implementing a real embedded backend.

The Linux and libcamera sources define the limitations the interfaces must not hide: [IPU3 discovery resets links before acquisition](https://github.com/libcamera-org/libcamera/blob/df8e348d64b4932a0676256ed24f0da3ee9438bc/src/libcamera/pipeline/ipu3/ipu3.cpp#L848-L898); [CIO2 uses a shared queue/DMA lifecycle](https://github.com/gregkh/linux/blob/988117cc1bb17338c586a4e21ade88b5397eac33/drivers/media/pci/intel/ipu3/ipu3-cio2.c#L482-L556); [IPU3 start and stop lose rollback or stop errors](https://github.com/libcamera-org/libcamera/blob/df8e348d64b4932a0676256ed24f0da3ee9438bc/src/libcamera/pipeline/ipu3/ipu3.cpp#L721-L784); [videobuf2 clears its started flag on a failed start](https://github.com/gregkh/linux/blob/988117cc1bb17338c586a4e21ade88b5397eac33/drivers/media/common/videobuf2/videobuf2-core.c#L1769-L1789).

### Ownership, observations and recovery

- A trusted owner must reserve both CIO2 and ImgU before discovery or any graph mutation, and retain control until restoration and verified release. Account for the exact affected endpoints, other clients, aliases, already-held references, inherited or transferred descriptors, mappings, helper/IPA workers and exported buffers. A device-open policy, an empty process scan, advisory locking, root privileges, or stopping PipeWire is not sufficient. The target trust boundary is the controlled kernel and supervisor, not an untrusted privileged host. Freeze a proposed dedicated lab boot/mediation boundary and prove its enforceable scope before any real graph is used.
- Keep one operation and reservation across RGB and IR. Do not leave a live manager eligible for discovery in the IR phase. Use accepted runtime formats, fresh request and queue generations, bounded extents and role provenance rather than device names, requested formats or synthetic IR/RGB substitutes. `ip3y` uses MPLANE even with one memory plane; do not change the ordinary single-planar queue.
- Obtain positive, loss-detectable evidence for real normal stop and partial-start rollback: driver-side ImgU completion, CIO2 receiver/DMA halt, sensor/transport outcome, and software drain, retirement, graph restoration and release. Bind each receipt to boot, loaded stack, graph, operation, reservation, phase and queue/stop generation. A worker's claim, `STREAMOFF=0`, callback disappearance or no warning is not enough. Require authoritative no-effect evidence for stages declared inapplicable. Leave instrumentation points and IPC serialization to the implementation plan, but do not let an observation source claim a stronger condition than it can verify.
- Durably record an unresolved attempt before the first possible effect. Keep a hold on lost ownership or any unknown cleanup, release or optical state. No following phase, retry, enrollment, grant or secret on a hold; restart, rollback and disable do not clear it. A known failure with verified cleanup may report bounded refusal, never silently continue. A separate reviewed recovery action may clear only the exact unresolved attempt after re-establishing authority and safe state with independently justified evidence. The durability and reconciliation mechanism needs its own review; filesystem bytes alone do not prove no rollback.
- The first authorized hardware qualification, not part of this approval, is attended, sequential, non-granting and uses a non-person target. Check each route alone, then both `RGB → IR → RGB` and `IR → RGB → IR`. Verify frame completeness against receiver evidence, generation and clock semantics, actual handover timing, graph restoration, and independent emitter measurements for baseline, bounded emission and OFF through release. Record consent, exact program/stack, limits, recovery and result scope before running. A dark frame, a cached strobe value or a rebuilt module name is not a measurement. An unattended proof contract requires its own exact-unit evidence; if it cannot be justified, do not enable unattended capture.

The Stage A hold checks cover interruption and process restart in isolated fixtures. A coherent disk/VM snapshot restore is a distinct case: do not advertise rollback-safe reactivation until a reviewed witness outside the rollback domain or an equally strong approved mechanism distinguishes a current state from a restored one. Once a restore is known or provenance is uncertain, keep activation off pending separately authorized recovery and fresh qualification. No TPM provisioning or other external witness changes in Stage A.

A dedicated boot, temporary exclusion of other camera clients and instrumented kernel/libcamera are candidates for the later lab design, not authorization to make those changes. Product use needs the same guarantees under an independently qualified product stack, or a separate qualification of whatever changes. Do not infer stock-stack support from an instrumented run, or silently impose a dedicated boot, packages or loss of desktop camera access on an opt-in user.

## 2. Admit and enroll the exact class

Before the feature can supply production auth input, approve a G0 decision for one exact native non-USB RGB+IR class, distinct from `ConnectedPair`, `SplitPair` and IR-only. Explicit opt-in selects only that class. Disabled, unknown, stale or mismatched state refuses before touching its camera, enrollment or secret paths. The lab profile and mock receipts cannot authorize it. Separate local qualification (G2), a single attended test/recovery authority (G3q), an account-authorized enrollment operation (G3a), and matching per-request authentication admission (G3b). They are not convertible.

Enrollment uses processed native RGB for the real required RGB anchor and bound native IR for the approved pairing/calibration. Do not synthesize, copy or reinterpret either role. Keep sequential posture regardless of timestamp skew until concurrency is separately qualified. Require valid inputs and the required RGB and IR PAD for G3a enrollment; an authorized first enrollment does not need an existing identity. G3b authentication also requires a current compatible enrolled identity and the supported IR-identity arm policy. Inference failure or insufficient required evidence refuses the operation. Before any real enrollment, independently qualify the exact input and PAD domains (G7/G8) with predeclared conditions, thresholds, outcome coverage and stop rules. If evaluation needs a temporary comparison reference, define its purpose, participant consent, isolated custody, retention and disposal in that separately approved protocol. It must never be a product enrollment or authorize any grant. No such reference is allowed in Stage A or the non-person transport trial. Share only categorical results, not frames, biometric material or credentials. Never update enrollment from authentication.

Use a protected, separately versioned experimental store outside stable discovery and an embedded class discriminator in the binding value that tested older readers refuse. Bind to the exact account, explicit profile, capture/calibration/model contract and immutable slot authorization instance. Revalidate current account enrollment/revocation, slot and operation authority after verified teardown. Commit the disposition, then atomically publish only a complete authorized enrollment (G9), preserving the old state on refusal. Before use, verify actual candidate-to-stable rollback and re-upgrade: ordinary store and password path survive, no implicit import or reactivation, no hidden change to legacy interpretation, and no hold is cleared. Do not assume candidate rollback works because two stable packages preserved an inert canary.

## 3. Keep warm unlock and cold sign-in distinct

Require one explicit local, on-demand face selection per attempt at both frontends. The class opt-in, a greeter appearing, an unlock prompt or a user walking up to the device is not consent to camera use. Do not enable `facefirst` or a background path. Qualify the actual selection and cancellation behavior in the pinned stock workers. Start with stock desktop components and narrowly scoped Irlume integration; if stock worker, transaction or wallet boundaries cannot provide the needed proof, stop that lane and propose a separately reviewed dependency change rather than weaken any check.

**Warm `kde`**: propose an explicit G10 expansion over ADR-0041's current `cosmic-greeter` predicate. Admit only the verified local KScreenLocker password worker, the requesting non-root account and a current active session. Prove the binding before any camera activity and again before returning a grant after confirmed teardown. Match service, process and session rather than assuming any same-UID process or string `kde` is the locker. No wallet request, helper or deferred release on this route; a locked KWallet remains locked.

**Cold interactive `sddm`**: separately approve the exact embedded class, cold purpose and wallet continuation (G10, G11 and an ADR-0003 decision); no inheritance from the warm lane. Use the existing mechanism only for `KdeWalletKey`, never release the Unix password on this path or put a wallet key into `PAM_AUTHTOK`. Require the normal local interactive SDDM transaction, not `sddm-autologin`, `sddm-greeter` or an arbitrary root RPC. The pinned [SDDM helper](https://github.com/sddm/sddm/blob/63780fcd79f1dbf81a30eef48c28c699ab15aded/src/helper/backend/PamBackend.cpp#L217-L278) shows auth, account, credential and session phases on one PAM object, but that fact alone gives the daemon no proof of continuation.

- Before opening a camera, verify the reviewed service/worker, scope, account, current slot, experimental activation and exact allowed secret/consumer. On success, perform final authority and connection checks only after verified teardown and durable disposition. An auth response may make a fresh, bounded, once-only continuation eligible but must carry no key. A new attempt or teardown cannot reuse that eligibility.
- The release design must prove, across PAM and daemon, that the same approved transaction passed account evaluation and reached its own local session hook after runtime setup. Bind the continuation to the exact worker/attempt, account, purpose, class and activation instance, intended wallet and receiving session. Trusted integration needs a positive source of that phase evidence, not a service string, cached token, caller assertion or a PAM handle address sent over RPC. Consume eligibility once before delivering the key; expiry, unknown proof, peer or session change, rollback or revocation stop release. Review the producer/consumer and interruption behavior before selecting a wire design. Prevent auth-phase secret stash and class-blind deferred `UnsealKeyring` from becoming alternative embedded release paths. No second automatic release after terminal delivery failure.
- The test wallet is the account's original supported local encrypted `kdewallet`, with its original salt, matching account password and no competing provider. Use an existing-only open contract. [KWallet `pamOpen`](https://github.com/KDE/kwallet/blob/27cd04696d8ce0f9b8b2ed0f7676ae3685ea7365/src/runtime/ksecretd/ksecretd.cpp#L1010-L1047) can create a wallet, so a simple earlier existence check, helper exit code or running daemon is not proof. If the provider/consumer cannot enforce the original-wallet restriction against loss or replacement, defer this lane or review a provider-bound change; do not substitute a newly created store. No wallet re-key. Record desktop and wallet outcomes separately.
- If the required wallet eligibility or purpose proof is missing before capture or invalid before the face response, refuse face and leave password fallback. After a valid face response, SDDM still owns the PAM account and session result: an account denial opens no session and releases nothing. If a valid session opens but the later continuation or key delivery fails, leave the existing wallet locked with no retry or alternate secret; do not retroactively turn the accepted face factor into a password prompt. That is a failed full-feature test, even if desktop sign-in succeeds.

Both frontends preserve existing typed-password and other supported factors. A refused, cancelled or timed-out face attempt may not initiate a retry, change account policy, or later turn into a grant. A correct password and actual rejected wrong password must be tested through the real provider, not inferred from a dialog or `PAM_IGNORE`.

## Validation and release gates

| Stage | Required evidence before advancing |
| --- | --- |
| A. Private linked proof | Exact toolchain/library/handler inputs recorded. Verify both orders on fixtures without a camera or credential capability; no normal entry point accepts fixture observations. Negative tests for wrong/missing/stale receipts, prior holder, incomplete rollback, timeout, observation loss, interruption and unresolved hold. Do not equate a linked build with receiver or optical evidence. Completion does not permit real adapter implementation or hardware use. |
| B. Product policy and desktop rehearsal | Review G0, storage/rollback, KDE G10 and cold SDDM G11/ADR-0003 decisions separately. Exercise disabled/default behavior, legacy readers, class isolation and recovery. Exercise the built PAM artifact with isolated policy, fixture daemon and test sink; test auth/account/session separation, wrong account/service/proof, stale or consumed continuation, failed delivery and password fallback. Use a separately scoped disposable reference desktop for packaged greeter, `setcred`, session, password wallet behavior and rollback. Fixture success cannot activate the hardware path. |
| C. Authorized live qualification | Exact-unit attended G3q with no real enrollment or auth uses the measured ownership, stop and optical protocol above. Separately qualify PAD/recognition before real G9 enrollment. Require an approved experiment and a reviewer for both warm and cold grants. No approval for one stage implies consent to another. |
| D. End to end | Warm unlock succeeds with no wallet effect. Cold boot starts with no prior open session/cache; capture completes and releases, PAM admits the account, only one approved wallet key reaches the intended consumer, and a pre-seeded synthetic marker in the same existing wallet is accessible without a password prompt or marker disclosure. Prove wrong-password, fallback, lost/revoked proof, missing/wrong wallet and disable/rollback controls. A running daemon, a newly created wallet or later manual unlock fails the wallet test. |

Keep deployments, hardware operations, reporter requests, security changes and publication separately authorized. Do not open a feature draft PR from Stage A or ask the reporter to compile it. If an owned exact unit is unavailable, propose one separately approved handoff of a reviewed, guarded non-granting lab candidate for the explicit transport/optical protocol, not an interim public product branch and not an authentication test. A later feature draft intended for contributor testing must contain a runnable experimental implementation with local software evidence and must state which exact-unit tests still remain; do not label it supported or unlock any unqualified route.

Every implementation slice must check current version-pinned upstream source, official documentation and relevant distro patches or advisories against the actual inputs it tests. Record sources, exact revisions, verification results and unresolved dependencies. Use the repository's real compiler, lints, guarded tests and independent review before advancing. A code-only result is not an attended or release qualification.
