# Distro PAM survey: how each family structures the stacks irlume wires

Date: 2026-08-30. Method: each family's container image with its real display
managers installed, the shipped service files extracted verbatim (they are now
permanent test fixtures), and the regeneration tools actually RUN against
wired files to observe what they touch. Everything below is evidence from this
run unless marked otherwise.

## The matrix

| Family | DM auth carrier | Dialect | Base stack owner | Regeneration tool | DM files regenerated? | irlume reachability |
|---|---|---|---|---|---|---|
| Arch (+ CachyOS/Manjaro/EndeavourOS) | `auth include system-login` (sddm), `system-local-login` (gdm) | inline include, `sufficient` recipe | pambase package | pambase package upgrade replaces `system-*` | NO (DM files are static, owned by the DM package) | `/etc/pam.d/<name>` exists; wired today |
| Debian (+ Ubuntu/Mint) | `@include common-auth` | `@include`, `sufficient` recipe | pam / libpam-runtime | `pam-auth-update` (manages ONLY the five `common-*` files) | NO (verified live: a wired `gdm-password` survives `pam-auth-update --package` untouched) | exists; wired today (Mint's cinnamon-screensaver live-validated earlier, #585) |
| Fedora (+ RHEL clones) | `auth substack password-auth` | atomic substack, `[success=1]` jump recipe | authselect (`/etc/pam.d/system-auth` -> `/etc/authselect/system-auth` symlink) | `authselect select ... --force` rewrites `/etc/authselect/*` | NO (verified live: a wired `sddm` survives `authselect select sssd --force`) | exists; wired today (SELinux lane handled separately) |
| openSUSE | `auth substack common-auth` | atomic substack, jump recipe (grammar.rs:22 already documents this dialect) | `common-*` autogenerated by pam-config ("All manual changes will be overwritten!") | pam-config rewrites `common-*`/`postlogin-*` | NO (irlume never edits those) | **GAP: DM pam.d ships ONLY in `/usr/lib/pam.d/`; `/etc/pam.d/` holds just the generated common/postlogin set, so irlume reads NotInstalled and skips wiring entirely** |
| NixOS | n/a (declarative `security.pam.services`) | n/a | the NixOS module system | config rebuild | n/a | by design via the shipped NixOS module (docs/NIXOS.md), never by editing files |

| Gentoo | expected Arch-like (`include system-auth`, pambase ebuild + pamd m4) | include | pambase ebuild | pamd m4 regeneration | expected NO | NOT surveyed hands-on (smallest user base); no evidence of a divergence beyond the openSUSE-style vendor-dir question |

## What was verified live (not just read)

1. **The transform handles every dialect on the real shipped files.** The 22
   fixtures under `crates/irlume-cli/tests/fixtures/pam/` are byte-for-byte the
   service files from the containers (archlinux:latest, debian:12-slim,
   registry.fedoraproject.org/fedora:44, opensuse/tumbleweed, each with sddm +
   gdm + lightdm installed). The new fixture test wires all twelve
   distro x {sddm, gdm-password, lightdm} combinations: every one takes the
   correct recipe branch (include -> `sufficient` line; substack -> `[success=1]`
   jump stanza), preserves the original carrier line, and is idempotent on a
   second pass.
2. **pam-auth-update (Debian 12):** with a face line inserted in
   `gdm-password` above `@include common-auth`, running
   `pam-auth-update --package` left the file untouched (the line survives) and
   `common-auth` unchanged on this run; structurally the tool manages only the
   five `common-*` files (they alone carry its header).
3. **authselect (Fedora 44):** with a face line inserted in `sddm` above
   `auth substack password-auth`, running `authselect select sssd --force`
   rewrote `/etc/authselect/system-auth` (symlinked from
   `/etc/pam.d/system-auth`) and left the wired `sddm` untouched.
4. **openSUSE placement:** `rpm -ql sddm`/`gdm` place their PAM services
   exclusively under `/usr/lib/pam.d/`; `/etc/pam.d/` on a fresh Tumbleweed
   contains ONLY the pam-config-generated `common-*` and `postlogin-*` set
   (18 files, no DM service).

## Findings

1. **Should-fix (the one real gap): openSUSE DM services are unreachable.**
   The recipes would wire them (the fixture test proves the transform works on
   openSUSE's own bytes); the Svc table never looks for them because there is
   no `/etc/pam.d/sddm` to find and no vendor entry. The fix is the
   plasmalogin precedent generalized: `vendor = Some("/usr/lib/pam.d/<name>")`
   for sddm/gdm-password/lightdm, materializing an `/etc` override from the
   vendor copy exactly as `login enable` already does for `plasmalogin`/`kde`
   on Arch/Fedora. Harmless on families that ship `/etc/pam.d` directly (the
   vendor path is only consulted when `/etc` is absent).
2. **Fine (verified, now pinned): the regeneration threat model holds.** Both
   regeneration tools own the BASE stacks, not the DM service files; irlume's
   lines live in the DM files; the self-heal's real exposure is a DM package
   upgrade shipping a fresh service file (covered by the `.pre-irlume` backup
   plus reconcile), not the distro tools.
3. **Fine by design:** `gdm-autologin` exists as a separate service on
   Arch/Fedora and is deliberately NOT wired (passwordless autologin performs
   no authentication); `gdm-fingerprint` is already a wired surface
   (fingerprint keyring lane); Fedora's `postlogin` and SUSE's `postlogin-*`
   fragments need nothing.
4. **Cosmetic:** Gentoo's layout was not verified hands-on; recorded as
   expected-Arch-like with an open question (whether any Gentoo setup uses a
   vendor directory like SUSE). No action until a user reports from it.

## Follow-ups this survey implies

- The openSUSE vendor-path issue (finding 1): one PR, the plasmalogin
  precedent applied to three services, fixture test extended to cover the
  materialize-from-vendor path.
- Alpine: one doctor/SETUP sentence saying PAM-less distros are unsupported
  (fail-closed) so a user there gets an explanation, not silence.

## Provenance

- archlinux:latest, `pacman -Sy pambase sddm gdm lightdm`

- opensuse/tumbleweed, `zypper install sddm gdm lightdm` (files read from
  `/usr/lib/pam.d`, the only place they exist)

  `authselect select sssd --force` (fedora:44).
